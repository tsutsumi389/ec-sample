# CLAUDE.md — `frontend/`

Next.js 側の固有規律。ここは `frontend/` 配下を触るときにだけ読み込まれる。

商品の可視性・実売価格・ゲストカート・ログイン後の戻り先・計測（`ProductCard` の器1つ／ファネルの段）など **バックエンドと共有するドメイン規律はリポジトリ直下の `CLAUDE.md`** にあるので、そちらも必ず読むこと。

- **アシスタントの開閉・幅は `lib/assistant-context.tsx` を通す**: 開閉状態・prefill・フォーカスの戻し先・**サイドバーの幅と接岸判定**は provider が持ち、`AssistantWidget` はパネルの描画と本文の押し出し・背景の `inert` を受け持つ。ウィジェット内部の `useState` に戻すと、行き止まりの画面（検索0件など）から `openAssistant()` で相談へ送れなくなる。ページから開くときは `returnFocusTo` に自分のボタンの ref を必ず渡すこと（渡さないと閉じたときフォーカスが画面の反対側の FAB へ飛ぶ）。**閉じた後のフォーカス復帰は effect で当てる**——FAB は開いている間 `display:none` で、`requestAnimationFrame` では再描画のコミット前に走って無言で外れる。`prefill` は入力欄に入れるだけで**自動送信しない**（サジェスト chip と同じ規律。予算や用途を書き足してから送れる状態にしておく）。
- **アシスタントに渡す「いま見ている画面」は `lib/assistantPageContext.ts` が全部持つ**: 経路の判定（`derivePageContext` / `isProductDetail`）も、ピルのラベル・取り下げの状態（`useAssistantPageContext()`）もこのファイル1つ。`AssistantPanel` は受け取って描くだけで、画面の種類ごとの都合を1000行超のチャット部品に溜めない（`lib/useAdminResource.ts` と同じ置き方）。**PDP かどうかの判定を別の正規表現で持たないこと**——`AssistantWidget` が FAB を固定購入バーの上へ逃がす判定も `isProductDetail()` を引く（別々に持つと「FAB は避けるのにコンテキストは送らない」食い違いが黙って生まれる）。**provider（`useAssistant()`）に足さないこと**——あの value は滅多に変わらない前提で分割してあり、遷移のたびに変わる値を混ぜると `openAssistant` しか使っていない `ProductListing` を巻き込む。**送っているものは必ずピルとして見えていて、必ず「×」で外せる**状態にすること（見えない前提が効くと、別の商品の話がしたい人に逃げ場が無くなる）。外した記憶は route と ID の鍵で持ち、別の商品ページへ移れば自動で復帰する。ピルの商品名は `GET /products/{id}` で引く（ページ本体が持っている商品オブジェクトを配ると、パネルが「どのページに何が載っているか」を知ることになる。PDP 自身も同じ取得をするので、接岸中は1往復ぶん重なる）。404 のときだけ送信ごと取り下げ、通信断は名前が出ないだけで送る。**「×」で外した場合と 404 の場合は同じ1つの state で持つ**（どちらも「この画面は前提にしない／次の商品で戻す」で挙動が同じ。分けると同じ規則を2度書くことになる）。検索結果など**クエリ文字列を要する画面を足すときは `useSearchParams()` の Suspense 境界**が要る（`usePathname()` だけなら不要）。
- **アシスタントの形は2つだけ**: **接岸（xl = 1280px 以上）** は右端に居座る非モーダルのサイドバー、**オーバーレイ（xl 未満）** は全画面のモーダル。中間の「浮いた小窓」を復活させないこと——窓の寸法を段階で切り替える仕組みと幅をドラッグで決める仕組みが同居すると、同じ「広さ」を2つの機構が別々に決めることになる。**接岸の境界を xl から動かさない**: Header のオフキャンバス・ドロワーが `xl:hidden` の `fixed inset-0 z-[55]` で、lg まで下ろすと 1024〜1279px でドロワーが右端＝サイドバーの真上に開く。PDP の固定購入バー（`lg:hidden`）も同じ理由で接岸域には出てこない。**JS 側の閾値は `lib/breakpoints.ts` の `MQ_XL` を引く**（Header の `matchMedia` と同じ1本。両者が一致していることが前提なので、別々のリテラルで持たない）。
- **接岸中は非モーダル。`inert` を張らないこと**: サイドバーは本文と併置される領域で、相談しながら商品を見て回れることが目的。背景に `inert`／フォーカストラップ／`aria-modal` を足すとその目的ごと消える（`role` も `complementary`）。**パネル内のリンクで遷移しても閉じない**——閉じると提案を1つ見るたびに会話が視界から消える。オーバーレイ側は逆に、全画面を覆うので `inert` もトラップも遷移時の close も必要（通さずに遷移すると `header`/`main`/`footer` の `inert` が残り、遷移先が一切操作できなくなる）。 **非モーダルなので、開いたまま `openAssistant()` が呼ばれうる**（背後の「相談する」ボタンが押せる）。パネルは再マウントされないので `prefill` の初期値は読み直されない——`prefillNonce` の変化を合図に入力欄へ入れ直す（渡さないと押しても何も起きないボタンになる）。
- **幅の出どころは provider の1つ。`--assistant-dock` は本文を詰めるためだけに配る**: サイドバーは `position: fixed` なので `body { padding-right }` では動かない。幅そのものは provider の state で、サイドバーはインラインスタイルで、本文は `AssistantWidget` が `<html>` へ置く `--assistant-dock` 経由で受け取る（`globals.css` §6）。**変数を直接書き換えても本文しか動かない**——幅を変えるときは必ず `setWidth()` を通すこと。右端に貼り付けず `--assistant-gutter`（縦スクロールバーの実測幅。`ResizeObserver` で測り直す）ぶん内側へ寄せるのは、`right: 0` だと文書のスクロールバーを覆ってつまみを掴めなくなる環境があるため。ドラッグ中は `<html>` の `data-assistant-resizing` が本文の補間を切る（付けたままだと本文が指から 280ms 遅れて追いかける）。**幅に `transition` を足さないこと**。
- **幅の下限・上限を知っているのは provider だけ**: クランプは `clampWidth()` の中だけで行い、ドラッグ側・キー操作側では計算しない。利用者が選んだ幅（保存値）とクランプ後の実効値を分けてあるのも規律で、一緒にするとウィンドウを一時的に狭めただけで好みの幅が削られ、広げ直しても戻らなくなる。`localStorage` への保存は掴んだ指を離したときだけ（`pointermove` ごとに書くと同期書き込みが毎フレーム入り、追従が目に見えて鈍る）。**ドラッグは掴んだ瞬間からの差分で幅を出す**——ビューポート右端からの絶対座標にすると接岸位置（gutter）を毎フレーム再導出することになり、接岸のしかたを変えた瞬間にドラッグだけがカーソルからずれる。
- **寸法の context はページ側の context と分けてある**: ページが引くのは `useAssistant()`（開閉の指令。value は滅多に変わらない）で、寸法は `useAssistantGeometry()`（`AssistantWidget` と `AssistantPanel` だけ）。1つに戻すと、`openAssistant` しか使っていない `ProductListing`（memo 無し・600行超）が `pointermove` ごとに再描画される。サイドバーの存在理由が「商品を見て回りながら相談する」である以上、一覧を背後に置いたままドラッグするのが主要動線なので、そこを重くしない。同じ理由で **`<html>`／`<body>` に効く副作用は `AssistantWidget` が一手に引き受ける**（`--assistant-dock`・`--assistant-gutter`・`inert`・`data-assistant-resizing`）。
- **サイドバー内の「広さ」の判断はすべてコンテナ基準**: バブルの行長・カードの列数・ヘッダーのラベル（`.assistant-header-label`）は器の実幅で決める（`globals.css` §6）。ビューポート基準の `sm:` を使うと、広い画面でサイドバーを狭めたときに判断だけが取り残される（実際、ラベルが残って見出し「Hibino の店員AI」を2行に折っていた）。
- **Webフォントは自己ホスト。`next/font/google` は使わない**: 和文は1ウェイトあたり約124個の unicode-range スライスに分割配信され、3書体で500個超になる。frontend コンテナには IPv6 経路が無いため一斉ダウンロードが大量に失敗し、**しかも next/font は失敗してもビルドを通して黙ってフォールバックに落ちる**（見出しが明朝でないことに気づけない）。`make fonts`（= `node frontend/scripts/fetch-fonts.mjs`）でホスト側から1回だけ取得し、`frontend/public/fonts/` と `frontend/app/fonts.css` を生成する。両者は `.gitignore` 済みで、`make up` / `make up-d` が未取得時のみ自動実行する。
- **明朝は 700 のみ・900 を指定しない**: Zen Old Mincho は 700 だけ収録している。持たないウェイトを指定するとブラウザが合成ボールドで太らせ、明朝の線が潰れる。`text-display` も 700 で組む。
- **明朝に `palt` は効かない**: 配信中の Zen Old Mincho サブセットに GSUB/GPOS が無く、`palt`/`pkna`/`kern` はすべて無効（実測済み）。カタカナのアキは `lib/wordBreak.ts` の `withWordBreaks()` が付ける `.kana` と `--kana-track` で詰める。
- **可変長の和文は `withWordBreaks()` を通す**: `word-break: auto-phrase` は Chromium で効かないため、`Intl.Segmenter` で語境界に `<wbr>` を挿すのが唯一の頼り。商品名・カテゴリ名・見出しに素の文字列を直接描画しないこと（語中改行が出る）。
