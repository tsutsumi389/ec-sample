08画面が無い作業と落とし穴

管理画面に用意されていないが、運用していれば必ず必要になる作業の手順。そして、各章で警告した「直感に反する挙動」を 1 枚にまとめた一覧。

この章の作業に共通する注意

ここに書かれた操作は管理画面の外側から直接データを書き換えるものである。次の 3 点は常に成り立つ。

  • 取り消しができない——UNDO も確認ダイアログも無い
  • 履歴が残らない——誰がいつ実行したか追跡できない
  • アプリ側の整合性チェックを通らない——画面経由なら弾かれる値も書き込めてしまう

したがって、更新・削除の前には必ず同じ条件の SELECT を実行して対象を目視すること。WHERE を書き忘れた UPDATE / DELETE は全行に効く。

8.1DB を直接操作する

接続は Makefile のターゲット 1 つで済む。

make db-shell
# 実体は docker compose exec db psql -U ec -d ecdb
# 抜けるときは \q

管理者を増やす（01 章）

会員登録で作ったアカウントを管理者に昇格させる。これが 2 人目以降の管理者を作る唯一の方法。

-- 1. 対象を確認する
SELECT id, email, name, role FROM users WHERE email = 'someone@example.com';

-- 2. 昇格する
UPDATE users SET role = 'admin' WHERE email = 'someone@example.com';

-- 3. 反映を確認する
SELECT id, email, role FROM users WHERE role = 'admin';
昇格したら入り直す

ブラウザ側はログイン時に取得した権限を保持しているため、昇格した本人は一度ログアウトして入り直すと管理画面のリンクが出る。降格させたいときは同じ要領で role = 'user' に戻す。

不適切なレビューを消す（07 章）

-- 1. 対象商品のレビューを新しい順に見る（product_id は商品の ID）
SELECT r.id, r.rating, r.comment, u.email, r.created_at
  FROM reviews r JOIN users u ON u.id = r.user_id
 WHERE r.product_id = 12
 ORDER BY r.created_at DESC;

-- 2. 消したい行の id を指定して削除する
DELETE FROM reviews WHERE id = 345;
削除すると再投稿できるようになる

「1 商品につき 1 人 1 回」の制限は既存のレビュー行で担保されている。削除すると、その利用者はもう一度投稿できる状態に戻る。

商品 Q&A の誤った回答を消す（07 章）

-- 1. 対象商品の Q&A を新しい順に見る
SELECT id, question, answer, source, answerable, created_at
  FROM product_questions
 WHERE product_id = 12
 ORDER BY created_at DESC;

-- 2. 消したい行の id（UUID 文字列）を指定して削除する
DELETE FROM product_questions WHERE id = '...';

-- 参考: AI が根拠を持てなかった回答だけを洗い出す
SELECT product_id, question, created_at
  FROM product_questions
 WHERE answerable = false
 ORDER BY created_at DESC;
最後の SELECT は商品の説明不足を見つけるのに使える

answerable = false が同じ商品に溜まっているなら、その商品の説明文か仕様に情報が足りていない。回答を消すより、商品側を書き足す方が根本の対処になる。

注文の明細と配送先を調べる（04 章）

出荷作業に必要な情報は管理画面に出ないため、ここで引く。

-- 未処理・支払い済みの注文を、配送先つきで一覧する
SELECT o.id, o.status, o.total_amount, o.discount_amount, o.coupon_code,
       u.name, u.email, o.shipping_address, o.created_at
  FROM orders o JOIN users u ON u.id = o.user_id
 WHERE o.status IN ('pending', 'paid')
 ORDER BY o.created_at;

-- 1 件の注文の明細（注文時点の商品名と価格が入っている）
SELECT product_id, product_name, price, quantity
  FROM order_items
 WHERE order_id = 1001
 ORDER BY id;

クーポンが何回使われたかを数える（05 章）

-- コード別の利用件数（キャンセル分を除く）
SELECT coupon_code, COUNT(*) AS uses, SUM(discount_amount) AS discounted
  FROM orders
 WHERE coupon_code IS NOT NULL AND status <> 'cancelled'
 GROUP BY coupon_code
 ORDER BY uses DESC;

8.2API を直接叩く

API ドキュメント（http://localhost:8000/docs）をブラウザで開けば、画面から実行できる。ここではコマンドの形も示す。

管理者トークンを取る

curl -s -X POST http://localhost:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@example.com","password":"admin123"}'
# => {"access_token":"eyJ...","token_type":"bearer"}

以降のコマンドでは、取得した値を TOKEN として使う。

TOKEN=$(curl -s -X POST http://localhost:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@example.com","password":"admin123"}' \
  | sed -E 's/.*"access_token":"([^"]+)".*/\1/')

全商品のベクトルを貼り直す（07 章）

curl -X POST http://localhost:8000/api/admin/recommendations/rebuild \
  -H "Authorization: Bearer $TOKEN"
# 即座に 202 が返り、処理は裏で進む。
# 進み具合と成否は make logs-backend で確認する。

注文の全項目を取る（明細・配送先を含む）

curl -s http://localhost:8000/api/admin/orders \
  -H "Authorization: Bearer $TOKEN"

下書きの実験を削除する（06 章）

作成をやり直したいときに使う。下書き以外は削除できない（400 が返る）。

curl -s http://localhost:8000/api/admin/experiments \
  -H "Authorization: Bearer $TOKEN"          # id と status を確認

curl -X DELETE http://localhost:8000/api/admin/experiments/3 \
  -H "Authorization: Bearer $TOKEN"

実験の名前・仮説・対象割合を直す（06 章）

curl -X PUT http://localhost:8000/api/admin/experiments/3 \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"name":"商品ページのセクション順","description":"レビュー先行の方が購入まで進むのではないか"}'
配信中に重み（weight）を変えない

枝の内容は下書きのときしか変更できないが、対象割合（traffic_allocation）は配信中でも API から変えられてしまう。配信中に配分をいじると割り当ての境界が動き、結果が設計とずれる。実施中の実験に対してこの API を使うのは、名前と仮説の書き直しに留めること。

8.3落とし穴の一覧

各章で警告した内容の索引。いずれも実装どおりの挙動であって不具合ではないが、知らずに操作すると事故になる。

領域起きること対処
商品 「削除」ボタンはアーカイブであり、管理一覧から行は消えない そういうものとして扱う。物理削除の手段は無い
商品 アーカイブ済みの商品を編集モーダルから保存すると、下書きに戻る 見るだけならキャンセルで閉じる。復活させたいときは意図してこれを使う
商品 商品コード（SKU）が重複すると「サーバーエラー」としか出ない 登録前に一覧で重複を確認する。前後の空白も別物として通る
商品 画像 URL と仕様は保存のたびにまるごと置き換えられる 編集時、意図せず行を消していないか保存前に確認する
商品 画像 URL を打ち間違えても保存でき、店頭ではプレースホルダが出るだけ 保存後に店頭の商品ページを目視する
価格 定価より高いセール価格が通り、どこにも異常の手掛かりが出ないまま高い方で売れる 桁を確認して保存し、店頭の価格表示を必ず目視する
価格 セールは自動で終わらない（期間の項目が無い） 終了日を管理画面の外で管理し、当日に手でセール価格を空にする
在庫 在庫は絶対値の上書き。モーダルを開いている間に入った注文の減算を打ち消す 開いたらすぐ保存する。保存後に在庫列を確認する
注文 管理側のキャンセルでは在庫が戻らない（購入者本人のキャンセルでは戻る） キャンセル前に明細を控え、商品編集で在庫を手で足す
注文 ステータスのプルダウンは確認なしで即確定し、順序も検査されない 行と注文番号を確認してから選ぶ。誤ったら選び直す（履歴は残らない）
注文 明細と配送先が画面に出ないため、出荷作業が管理画面だけで完結しない 8.1 の SQL か 8.2 の API で引く
クーポン 使用回数を制限できず、同じ人が何度でも使える 期限を短く切る、配布先ごとに別コードを発行する、大きな割引には最低注文金額を併用する
クーポン 割引率に上限が無く、100% 超も保存できる（＝常に全額無料） 保存後に一覧の「割引」列を読み返す
クーポン 期限切れでも一覧では「有効」バッジのまま 有効期限の列を見る。定期的に棚卸しして無効化する
A/Bテスト 配信を始めると枝の内容を直せず、同じキーで作り直すこともできない 開始前に設定値を店頭で目視確認する。「終了する」は不可逆
A/Bテスト フロントが読まないキーで実験を作っても、画面は何も変わらない 使えるキーは pdp_section_order と pdp_cta_copy の 2 つだけ
検索 Ollama が止まっているとベクトル更新に失敗するが、画面には何も出ない 大きく書き換えたあとは make logs-backend を見る。まとめて直すなら 8.2 の再構築
カテゴリ カテゴリを削除しても、所属していた商品の検索用ベクトルには旧カテゴリ名が残る 該当商品を開いて保存し直すか、全件を再構築する
Q&A AI の回答が誤っていても、管理画面から直すことも消すこともできない 商品の説明・仕様を充実させて予防する。事後対処は 8.1 の SQL
レビュー 管理画面から削除も非表示もできない 8.1 の SQL で削除する
全体 変更履歴・監査ログが一切残らない 戻す可能性のある変更は、変更前の値を手元に控えてから行う
