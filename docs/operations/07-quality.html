07カタログ品質と顧客接点

検索とレコメンドの土台、そして購入者との接点（レビュー・商品 Q&A・アシスタント）。この領域には管理画面がほとんど無く、運用の大半は「書いた内容が自動でどう使われるか」を理解しておくことに尽きる。

7.1商品の文章が検索精度を決める

検索とおすすめは、商品ごとに作られる「意味のベクトル」に基づいて動く。このベクトルの元になる文章は、次の内容をつないで自動的に組み立てられる。

元になる項目運用上の意味
商品名最も強く効く。略称だけでなく一般名詞を含めておくと拾われやすい
カテゴリ名未分類の商品は「その他」として扱われる
説明用途・シーン・特徴を書くほど、曖昧な言い回しの検索に当たるようになる
価格帯金額から自動で決まる。入力項目ではない
仕様素材・容量などが説明文の書きぶりに左右されずに検索へ乗るようにするため、仕様行もベクトルに含まれる。仕様を埋めるほど検索に強くなる
運用としてやること

特別な操作は無い。商品を丁寧に書くことがそのまま検索対策になる。とくに仕様欄は、商品ページの見栄えのためだけでなく検索のためにも効く。逆に、説明が 1 行しかない商品は検索に出にくい。

7.2商品を保存すると裏で起きること

  1. 商品の作成・編集を保存すると、商品自体の変更は確実に保存される（ここが失敗することはない）
  2. その直後、裏でその 1 商品のベクトルが作り直される
  3. 続けて、全商品の内部的な分類 ID が振り直される
ベクトルの更新に失敗しても、画面には何も出ない

ベクトルを作るには ホスト側で Ollama が動いていて、対象のモデルが取得済みである必要がある。落ちていれば更新は失敗するが、管理画面には成功も失敗も表示されない。商品の保存だけが済んで、検索用のベクトルは古いまま残る。

確認する唯一の方法は make logs-backend でバックエンドのログを見ること。失敗していれば「ホストの Ollama が起動しているか、対象モデルが pull 済みか確認してください」という趣旨の警告が出ている。説明文を大きく書き換えたときは、保存後にログを一度見ておくと取りこぼしに気づける。

7.3全商品のベクトルを貼り直す

Ollama が止まっていた間に何件も編集してしまった場合など、まとめて作り直したいことがある。手段は 3 つ。

手段範囲やり方
バックエンドの再起動 差分のみ（文章が変わった商品・まだベクトルが無い商品だけ） make restart。起動時に自動で走る。取りこぼしの回収はこれで足りることが多い
API を直接叩く 全件を強制 POST /api/admin/recommendations/rebuild。手順は 08 章
1 商品ずつ保存し直す その商品のみ 編集モーダルを開いて何も変えずに保存する
全件再構築のボタンは管理画面に無い

API は用意されているのに、それを呼ぶ導線が管理画面のどこにも無い。実行するには API ドキュメント（http://localhost:8000/docs）か curl を使う必要がある。日常運用では使わないが、Ollama のモデルを入れ替えたときなどには必要になる。

Ollama が使えない環境では

検索は通常のキーワード検索に、おすすめは人気順に、それぞれ自動的に切り替わる。アプリが落ちることはないので、AI 機能を使わない構成でも運用自体は成立する。商品 Q&A も定型の文言を返す。

7.4レビュー

購入者が商品ページから投稿する。運営の操作は無い。

項目内容
投稿できる人ログイン済みで、その商品を買ったことがある人。キャンセル以外の注文に含まれていればよく、まだ入金前（未処理）の注文でも投稿できる
回数1 商品につき 1 人 1 回。書き直しはできない
内容星 1〜5（必須）とコメント（任意）
閲覧未ログインでも読める
不適切なレビューを管理画面から消す手段は無い

レビューの削除・非表示・返信のいずれも、管理画面にも API にも存在しない。投稿した本人ですら消せない。対処は DB を直接操作するしかない（手順は 08 章）。

レビューは全件がまとめて読み込まれる

星の分布（★5 が何件、★4 が何件…）は、取得したレビューを画面側で数えて出している。ページングは無いため、1 商品のレビューが数百件を超えると商品ページが重くなる。そこまで増える見込みが出たら、運用でしのぐのではなく実装を見直す段階にある。

7.5商品 Q&A

  1. ログイン済みの購入検討者が、商品ページから質問を書く（300 文字まで）
  2. その場で AI が回答を生成し、すぐに公開される。根拠にするのはその商品の説明文とレビューだけで、他の商品の情報は混ざらない
  3. 回答には「根拠を持って答えられたか」の判定が付き、情報が足りない場合はその旨が示される
  4. Ollama が動いていない場合は、定型の案内文が回答として保存される
AI の回答に人が手を出せない

商品 Q&A には管理画面が無い。質問の一覧を見ることも、AI の回答を直すことも、消すことも、人が代わりに答えることもできない。誤った回答が公開されても、そのまま商品ページに残り続ける。

現状これに対処する運用は 2 つしかない。

  • 予防：商品の説明文と仕様を充実させ、AI が根拠にできる情報を増やしておく（回答の質はほぼこれで決まる）
  • 事後：DB を直接見て、問題のある回答を削除する（08 章）

7.6AI アシスタント（店員 AI）

店頭の全ページに常駐するチャット。商品を提案する役割で、提案できるのは実在する商品だけに制限されている（候補に無い商品を勝手に作り出さない仕組みが入っている）。運営の操作は無い。

会話ログを管理画面から読めない

会話は保存されているが、一覧を取得する手段が用意されていない（自分の会話しか読めない仕組みのため）。「利用者が AI に何を聞いているか」を知るには DB を直接見るしかない。
なお、管理画面ではアシスタントのボタン自体が表示されない。

7.7ホームのおすすめ

ログイン中の利用者には、閲覧・購入・お気に入りの履歴から作られたおすすめが出る。生成は裏で自動的に走り、出来上がるまでは人気順が表示される。運営が起動したり止めたりする操作は無い。

おすすめに出したくない商品があるとき

おすすめから個別に除外する設定は無い。おすすめは店頭に並んでいる商品（＝一覧に出る状態の商品）からしか選ばれないので、出したくなければ販売状態を変えるしかない。

7.8ユーザー管理

/admin/users は ID・名前・メールアドレス・権限 の 4 列を並べるだけの画面で、ボタンもリンクも 1 つも無い。

ユーザーに対してできることは何も無い

権限の変更、退会・凍結、パスワードのリセット、そのユーザーの注文履歴を見ること、検索——すべて実装されていない。管理者を増やす操作を含め、必要なら DB を直接触ることになる（08 章）。登録日時はサーバーからは返っているが画面には出ていない。
