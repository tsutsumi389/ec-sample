04受注〜出荷〜完了

注文が入ってから配達完了まで、運営がする操作は プルダウンを 1 段ずつ進めることだけである。決済も配送も外部と繋がっていないため、ステータスは「実際に起きたこと」を人が記録する台帳として使う。

4.1注文が入った時点で済んでいること

  1. 購入者がカートから注文を確定した時点で、在庫は既に減っている（同時注文でも売り越さないよう、確定処理の中で押さえられる）
  2. 注文明細には、その時点の 商品名と実売価格が写し取られている。あとで商品を編集しても注文の金額は変わらない
  3. クーポンが使われていれば、確定時にもう一度検証されたうえで割引額が確定している
  4. カートは空になり、注文は 必ず「未処理」（pending） で作られる

4.25 つの注文状態

pending
未処理。注文直後の状態。入金確認待ち。
購入者がキャンセルできる
paid
支払い済み。入金を確認したら運営が手で進める。
購入者がキャンセルできる
shipped
発送済み。荷物を出したら進める。
購入者がキャンセルできる
delivered
配達完了。この状態になって初めてレビューの前提が満たされるわけではない点に注意（レビューはキャンセル以外なら書ける）。
購入者がキャンセルできる
cancelled
キャンセル。購入者の履歴では打ち消し表示になる。
購入者がキャンセルできる
購入者側の見え方

購入者のマイページには「注文受付 → お支払い → 発送 → お届け完了」の 4 段のタイムラインが出る。運営がプルダウンを進めると、購入者の画面でもその段が進む。キャンセルはタイムラインに乗らず、打ち消し表示になる。

4.3日々の受注処理

  1. /admin のダッシュボードで「最近の注文」5 件を眺め、新しい注文が入っているかを確認する
  2. /admin/orders を開く。新しい順に全件が並ぶ。絞り込みが無いので、未処理の注文は目視で探す
  3. 入金を確認したら、その行のプルダウンで「支払い済み」を選ぶ。選んだ瞬間に確定する（確認ダイアログは出ない）
  4. 何を何個送るかはこの画面には出ないので、別途確認する（4.4 を参照）
  5. 荷物を出したらプルダウンで「発送済み」を選ぶ
  6. 到着が確認できたら「配達完了」を選ぶ。これで一件が終わる
プルダウンは確認なしで即確定し、順序も検査されない

「配達完了」から「未処理」へ戻すような遷移も、そのまま通ってしまう。取り消し（undo）は無く、変更履歴も残らないので、誤って選んだときは正しい状態を選び直すしかない（誰がいつ間違えたかは追跡できない）。行を選ぶときは注文番号を必ず確認すること。

出荷に必要な情報が管理画面から得られない

注文明細と配送先は、サーバーからは返っているのに画面に描かれていない。したがって「何を、どこへ送るか」を管理画面だけで知ることはできない。現状の手段は次の 2 つ。

  • make db-shell で注文明細と配送先を直接引く（手順は 08 章）
  • API ドキュメント（http://localhost:8000/docs）から GET /api/admin/orders を実行し、返ってきた JSON を読む

どちらも管理画面の外の作業になる。受注件数が増えるほど、この一手間が運用の律速になる。

4.5キャンセルの 2 つの経路

「キャンセル」と呼ばれる操作は 2 つあり、在庫の扱いが違う。ここを取り違えると在庫がずれる。

経路できる条件在庫備考
購入者がキャンセル
マイページの注文詳細から		 その注文が「未処理」か「支払い済み」のときだけ 自動で戻る 確認ダイアログ（「この操作は取り消せません」）が出る。運営の操作は不要
運営がキャンセル
注文管理のプルダウン		 いつでも（発送済み・配達完了からでも通る） 戻らない 在庫を戻したければ、続けて商品編集で手入力する

運営側でキャンセルするときの手順

  1. キャンセルする注文の明細を先に控える（何をいくつ戻すのかが後から分からなくなるため。明細の調べ方は 4.4）
  2. 注文管理のプルダウンで「キャンセル」を選ぶ
  3. /admin/products で該当商品を開き、在庫数に控えた数量を足した値を入力して保存する（商品が複数あるなら 1 つずつ繰り返す）
  4. 一覧の在庫列で、加算後の数値になっていることを確認する
キャンセルされた注文からも「もう一度買う」ことはできる

購入者は、キャンセル済みの注文からでも同じ商品をカートへ入れ直せる。その際、買えなくなっている商品や在庫が足りない商品はエラーにせず見送られる（1 件の在庫切れで一括投入ごと失敗させない設計）。運営側の操作は不要。

4.6外部との連携は無い

決済・配送・通知は、いずれも実際には起きない

「支払い済み」にしても決済は発生せず、「発送済み」にしても配送業者へは何も飛ばない。追跡番号・配送業者・出荷日を記録する項目も無く、購入者へのメール通知も送られない。ステータスは実世界で起きたことを人が後追いで記録する台帳であり、システムが何かを実行するトリガーではない。

また、商品ページに出ている「14 時までのご注文で翌営業日に出荷いたします」「全国一律 送料無料」「30 日間の返品保証」は固定の文言で、これを裏づける処理は実装されていない。運用としてこの約束を守れるかどうかは、管理画面の外の話になる。
