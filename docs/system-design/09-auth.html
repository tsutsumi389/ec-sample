09認証・認可設計

JWT（HS256、Bearer トークン）によるステートレス認証を提供し、bcrypt でパスワードをハッシュ化する。トークンは user_id を sub に持ち、有効期限は 24 時間。サーバ側トークンストアやブラックリストは持たない。

9.1トークンと依存性

依存性挙動
get_current_user必須認証。HTTPBearer(auto_error=True) でヘッダを要求し、検証済み User を返す
get_current_user_optional任意認証。HTTPBearer(auto_error=False)。ヘッダ無し・無効・期限切れ・失効・削除済みでも 401 を投げず None（匿名）を返す。レコメンド等のフォールバック用
get_current_admin管理者認可。get_current_user に依存し role≠admin なら 403（Admin privileges required）

9.2パスワード変更時の全セッション失効

  1. update_password で current_password を検証（不一致は 400）
  2. new_password を bcrypt で保存し、password_changed_at を秒精度（microsecond=0）に丸めて記録
  3. 以後 _resolve_user_from_token でトークンの iat が password_changed_at より前なら 401 にして失効させる
  4. 秒に丸めるのは、変更直後の再ログインで得た同一秒 iat の新トークンが誤失効しないため

9.3セキュリティ上の取り決め

  • login はメール不在・パスワード不一致を区別せず一律 401「Incorrect email or password」（ユーザー列挙防止）
  • register は既存メールを 400 で拒否。新規ユーザーは常に role=user（管理者昇格の API 経路は無い）
  • 認証失敗時の 401 応答には常に WWW-Authenticate: Bearer ヘッダを付与
  • 認可は role 文字列で判定（user / admin）。細粒度の権限は無い
  • リフレッシュトークンの仕組みは無い（有効期限 24h 固定）

9.4MCP サーバー（/mcp）の認証

MCP ツール（§6.7）も同じ JWT を使う。OAuth 2.1 は実装せず、MCP 側に login ツールも置かない（会話ログにパスワードを載せないため）。トークンは POST /api/auth/login で取得したものを MCP クライアントの Authorization: Bearer ヘッダに設定する。

  • ヘッダは Context から読み、必ず _resolve_user_from_token を通す（jwt.decode を自前で書くと iat / password_changed_at の失効判定が効かなくなる）
  • 身元はツール呼び出しのたびにヘッダから引き直す。ユーザーをモジュール変数やセッションにキャッシュしない（最初の呼び出し時点の身元に固定され、以後の全操作がその人として動く）
  • 認証必須ツールは fail closed（require_user）。無効・期限切れのトークンを匿名へフォールバックさせない。任意認証は search_products だけで（optional_user）、こちらは無効トークンを匿名に落とす
  • visitor_id（X-Visitor-Id）は読まない。計測専用の端末 ID であり認証には使わない
  • Host / Origin の検査（DNS リバインディング防護）はアクセス制御ではない。どちらもクライアントが自由に書けるヘッダで、curl のような非ブラウザには効かない。/mcp の露出面の防御は各ツールの認証が担い、既存の /api と同等になる
確認トークン

preview_checkout が発行し place_order だけが受け取る confirm_token は、テーブルを増やさないためのステートレスな署名トークン。鍵は環境変数を 2 本目に増やさず、同じ SECRET_KEY から HMAC-SHA256 で用途専用の鍵を派生させて使う（2 本目を用意すると fail closed の検査・make secret の生成・compose の受け渡し・ローテーション手順がすべて二重になり、忘れたときに「無ければ SECRET_KEY にフォールバック」と書きたくなる＝既定値そのもの）。分離は運用ではなく暗号で取る——派生鍵から SECRET_KEY は復元できないため、JWT の署名鍵と計算上独立になる。加えて署名対象の先頭に用途文字列を、トークン本体に hbc1_ の接頭辞を置き、JWT（aaa.bbb.ccc）と一目で見分けがつくようにしてある（ログや会話に現れたときに「これはセッショントークンではない」と分かること自体が防御になる）。
SECRET_KEY をローテーションすると発行済みの confirm_token も一斉に無効になる（下見からやり直しになるだけで、注文には影響しない）。

署名鍵

JWT 署名鍵 SECRET_KEY は環境変数からのみ取得し、既定値へのフォールバックは持たない。未設定・32文字未満・既知の弱い値（dev-secret 等の前方一致）のいずれかなら app/auth.py の _load_secret_key() が起動時に RuntimeError を投げて落とす（fail closed）。鍵は make secret がデプロイごとに openssl rand -hex 32 で .env に生成し、compose がそこから読む。make up / make up-d / make reset は未生成時のみ自動で走る。
HS256 は対称鍵なので、鍵の共有は管理者トークンの発行権限の共有と同義。しかも漏洩時はパスワード変更で締め出せない——失効判定は iat と password_changed_at の比較であり iat は発行側が選べるため、復旧手段は鍵のローテーションだけになる。
