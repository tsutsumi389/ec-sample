# CLAUDE.md — `mcp-apps/`

`/mcp` の View（iframe の中で描画される画面）を持つコンテナ。TypeScript + React + Vite。ここは `mcp-apps/` 配下を触るときにだけ読み込まれる。

backend 側の規律（`_meta.ui` の組み立て・UI リソースの登録順序・dist が無いときのフォールバック）は `backend/app/mcp_server/CLAUDE.md` にある。**ツールの入出力の契約は backend 側が唯一の源**であり、`src/shared/types.ts` はその凍結した写しなので、backend を直してから写しを追随させること。プロジェクト全体の規律はリポジトリ直下の `CLAUDE.md`。

- **MCP Apps の View（`/mcp` の画面部分）は別コンテナ `mcp-apps/`（TypeScript + React + Vite）が持ち、backend は読むだけ**: backend が触るのは `app/mcp_server/ui/dist/{search,product}.html` だけで、これは `mcp-apps` コンテナが watch ビルド（`npm run dev`）で書き出す生成物（`.gitignore` 済み。リポジトリには入らない）。MCPServer 本体・11ツール・在庫/価格/購入可否の判定・`confirm_token`・`_meta.ui` の組み立て（`build_search_ui_items` / `build_product_ui_item`）は backend に残っており、**移してあるのは iframe の中で描画される View だけ**。SDK は `@modelcontextprotocol/ext-apps` を npm の正規依存として **1.7.5 に厳密固定**で入れる（`mcp==2.0.0` を固定しているのと同じ規律。`globalThis.__McpAppSdk` を経由する vendor ハックは廃止済み）。Vite の `build.outDir` は `mcp-apps/` からの相対 `../backend/app/mcp_server/ui/dist` で、compose のマウント（`./backend/app/mcp_server/ui:/backend/app/mcp_server/ui`）は**この相対パスがホストでもコンテナ内でも同じ場所に解決される**ように置いてある——出力先を環境変数で切り替えないための配置なので、マウントの位置を変えたり外したりしないこと。`node_modules` を匿名ボリュームに隔離するのも必須で、bind mount 側に置くと alpine 用のネイティブバイナリがホストへ降り、ホストでの `npm run build` が壊れる（逆向きも同じ）。**dist が無ければ UI を諦めて素のツール登録に落ちる規律は不変**（`backend/app/mcp_server/CLAUDE.md`）。ただし compose の backend は `depends_on: mcp-apps: {condition: service_healthy}` で dist の2枚が揃うのを待つので、**開発環境でビルドが恒久的に失敗すると backend も起動しない**——フォールバックが実際に効くのは「compose を通さず backend だけ動かした場合」と「dist はあるが中身が壊れている場合」の2つ。UI が付かないまま気づかず開発を続けるより待たせるほうを取った、という判断であって、フォールバックを外してよいという意味ではない。**View を直したら backend の再起動が要る**: HTML は `apps_ui.py` の **import 時に一度だけ**読まれるため、dist が書き換わっても再起動しなければ古い UI が配られ続ける。compose の backend は `uvicorn --reload-include '*.html'` でこれを自動化しており、**`uvicorn[standard]`（= watchfiles）が前提**——素の `uvicorn` に落とすと StatReload になり、`--reload-include` は warning を出して無視される（HTML の変更が反映されない静かな劣化）。`mcp-apps/src/shared/types.ts` は `views.py` の `structuredContent` と `ui_assets.py` の `_meta.ui` の**凍結した写し**であり、**唯一の源は backend 側**。ツールの入出力を変えるときは backend を直してから写しを追随させること（写しを先に動かすと契約が2つになり、必ず片方が古くなる。`0004` の `SPECS_BY_SKU` が `seed.py` の写しであるのと同じ関係）。
- **MCP Apps の View は React（TSX）で書き、SDK の import は `@modelcontextprotocol/ext-apps/react` 1本に統一する**: エントリ HTML（`mcp-apps/{search,product}.html`）が持つのは `<div id="root">` だけで、画面は `*View.tsx`、状態（`useReducer`）と「その View だけの判断」は `use*View.ts`、**どの View でも同じホストとの接続手順（`useApp` / `useHostStyles` / safe area / 接続失敗の検出）は `shared/useHostApp.ts`** が持つ。接続手順を `use*View.ts` へ書き戻さないこと——順序と締切の規律（下記）が View の数だけ増える。逆に、失敗をどう見せるか（全面エラーかバナーか）は View の判断なので `useHostApp` は持たず、文言だけを返す（`shared/openLink.ts` が「文言は持つが表示の仕方は持たない」のと同じ分担）。**エントリ HTML に骨組みを書き戻さないこと**——`createRoot().render()` は器の中身を必ず作り直すので、静的に置いた要素は一瞬だけ見えて消える。**SDK のルート（`@modelcontextprotocol/ext-apps`）と `/react` はそれぞれ `App` クラスの実体を持つ別々のバンドル**なので、両方から import すると同じクラスが2つ入る（33KB 増え `instanceof` が食い違う）——`/react` がルートを丸ごと再エクスポートしているので型も値もこちら1本で足りる。App の生成・接続は `useApp` に任せる（`onAppCreated` が `connect()` の**前**に呼ばれるので、一度きりの通知の購読はそこに書く。手で `new App()` する形に戻すとこの順序を自分で守り続けることになる）。テーマ・CSS 変数・フォントは `useHostStyles` に任せ、**`shared/host.ts` が持つのは SDK が扱わない safe area だけ**。購読は `addEventListener` を使い `app.on*` の setter を使わない（setter は単一ハンドラの置き換えなので `useHostStyles` と奪い合う。SDK 自身が deprecated にしている）。**`dangerouslySetInnerHTML` はどこにも書かない**——移植前に `innerHTML` を1つも使わなかったのと同じ規律で、抜け道の名前が変わっただけ。**StrictMode で包まない**（effect が2回走って接続が二重になり、一度きりの通知をどちらが受けるか不定になる）。押せる／押せないは必ず `disabled={...}` の式＝状態からの派生で書くこと（移植前は `setLoading()` と `resetControlsToConfirmed()` の2か所が DOM を書き換えており、経路によって片方だけ通る食い違いが実際に起きていた）。
- **`mcp-apps/package.json` に依存を足したら `make mcp-deps`。`make up-d` では反映されない**: `node_modules` は匿名ボリュームでコンテナ側に隔離してあり、`docker compose up` は**コンテナを作り直しても匿名ボリュームは引き継ぐ**ため、イメージだけ新しくなって中身は古いまま残る。そのまま watch ビルドが走ると、解決できなかった依存が `import ... from "react-dom/client"` の形で残った HTML が dist へ書き出され（ビルドは非ゼロ終了するが**ファイルは書かれた後**）、backend はそれを読んで白画面の View を配る——`/mcp` のツールは 11 本のままなので `make mcp-check` でも気づけない。React を入れたときに実際に踏んだ。いまは `scripts/check-dist.ts` が「インライン化された script に module specifier が残っていないか」を見て**書く前に**落とすので dist は直前の正常な HTML のまま残るが、それは受け側の防御であって、依存を入れ直す手順を省いてよいという意味ではない。同じファイルの script タグの検査を**開き／閉じの個数一致に戻さないこと**——react-dom が `'<script>'` という文字列リテラルを持ち込むので恒久的に誤検知し、しかもその下駄が本物の破損（生の `</script` 混入）と相殺して素通しする。

## 検証

**`package.json` を変えたときは `make mcp-deps`**（匿名ボリュームの `node_modules` は `make up-d` では入れ替わらない）。そのうえで `make mcp-typecheck` を通す（**ビルドは型を見ない**——Vite 8 は rolldown/oxc で型注釈を落とすだけなので、型エラーがあってもビルドは成功しログにも出ない。フロントの `make lint` にあたる）。あわせて `make logs-mcp-apps` でビルドが通っているか確認する（watch ビルドが常駐しているので、通常は保存するだけで dist が更新される。取りこぼしたときは `make mcp-ui-build`）。そのうえで `make mcp-check` を叩き、ツールが 11 本見えることと「UIリソース」に `ui://` が2本（検索・商品詳細）載ることを確認する。**dist の更新だけでは反映されない**——backend が再起動して読み直すまで古い UI が配られる（compose の `--reload-include '*.html'` が拾うので、`make logs-backend` に再起動のログが出るのを待つ）。
